# 军官对战斗做什么

[English](officer_effects.md)

本索引锚定 build 2259。它说明一名军官会往它所瞄准的单位身上写下什么修正、这些修正
怎么编码、各自又够得着哪些单位。军官对**账本**做什么——折扣、收入、发的队伍——是
[`reinforce_items.md`](reinforce_items.zh.md) 和
[`config/officers.yaml`](../../config/officers.yaml) 的事。

机器可读的表是
[`config/officer_effects.yaml`](../../config/officer_effects.yaml)，由
`scripts/extract-officer-effects.py` 从 build 自己的 `ConfigDataContainer` 写出。
build 的 132 名军官里，79 名带有修正。

**这些数字拿游戏自己的话核对过。** [`officers.md`](officers.zh.md) 用本地化文案列出每名
军官的效果，那是从 build 2227 用完全另一条路读出来的。79 名里有 73 名在那边写了百分比，
而每一个百分比都在这张表里：空军专家的"攻击 +13%、生命 +13%"就是 `damage_rate` 和
`life_rate` 的 `+0.13`，先进进攻战术的 30% 就是 `+0.3`，先进飞弹装置的 200% 就是
`land_mine_rate` 的 `+2`。提取脚本在发现不一致时**拒绝写表**，所以一次误解析必须同时和
一个更早 build 的独立读法对上才能蒙混过关。

## 它落在哪里

军官是一个修饰符，不是一条自己的规则。`Officer.AddData` 把军官交给
`MechDataModifer.TryAddCommonData`，再到 `MechDataModifer.AddData` 和
`SkillDataModifier.AddData`——正是
[`architecture.md`](../spec/simulation/architecture.zh.md) 说的那两层覆盖，一层在单位
上、一层在它的技能上。军官本身就是给每条条目打标签的那个 `IDataModifier`，所以把军官
拿走，它写的修正也跟着走。

这些字段就是 `GameRiver.OfficerData` 用来实现
`ICommonMechDataChangeDataSource` 的那一组。`TechnologyData`、`EquipmentData` 和
`EnergyTowerSkillData` 实现的是同一个接口，所以一种表的形状服务四个来源；另外三个等它们
各自的对象被解析出来就并进这张表。

## 一个数怎么读

| 种类 | 编码 | 例 |
| --- | --- | --- |
| `*_rate` | `FPoint`，Q32.32 原始整数 | `1288490188` 是 `+0.3` |
| `*_value` | `FPoint`，单位是那个数自己的单位 | `42949672960` 是射程 `+10` |
| `speed_value`、`extra_life`、`exp_rate` | 普通整数，由运行时 getter 的返回类型决定 | `3` |

文件里存的是**原始整数**，因为那才是 build 存的、也是定点模拟需要的。每行后面的注释是同
一个数读成小数的样子，之所以只是注释，是因为小数才是有损的那个：`1288490188 / 2^32` 是
`0.29999999981`，而 build 从不拿 `0.3` 去算。

## 一条比率怎么合成

比率对描述**乘一次**，同一个数上的两条比率**先相加再乘**：
`base × (1 + Σ add − Σ reduce)`，向零截断，不是四舍五入。

`scripts/officer-composition.mcscript` 对着游戏把它测了出来。一个长弓打一个犀牛，打两
下，三份录制里犀牛都活到最后，所以读数就是它在 19297 里还剩多少：

| 蓝方军官 | 犀牛剩余生命 | 每击伤害 |
| --- | ---: | ---: |
| 无 | 14639 | 2329，描述原样 |
| 先进进攻战术 | 13243 | 3027 |
| 先进进攻战术 ×2 | 11845 | 3726 |

3027 是 `trunc(2329 × 1.3)`，3726 是 `trunc(2329 × 1.6)`。若两条比率连乘，就是
`trunc(2329 × 1.69)` = 3935、剩 11427，而游戏打出来的不是这个数。截断在第一个数上就已经
看得见：`2329 × 1.2999999998` 是 3027.6999，build 留下的是 3027。

录像还从问题的**另一头**把同一件事说了一遍。`once` 那份在长弓的**技能**通道里存着
`damage_rate.add = 1288490188`，正是军官表里的 `+0.3`；`twice` 那份存的是
`2576980376`，恰好是它的两倍。**build 在写入的时候就把两名军官加好了**，所以录像里是一
条 `+0.6`，不是两条 `+0.3`——模拟器把条目求和，是在照抄 build 存的样子，而不是自己发明
一个条目间的顺序。两份录像里单位覆盖层和 buff 聚合都是中性的：这名军官的伤害根本不落在
单位上。

`crates/simulation/src/data.rs` 实现的就是这条规则，并且**拒绝**这次捕获没够着的两种情
况：`*_value` 修正（没人测过它怎么合成），以及同一个数被两条通道同时修正（没人测过顺
序）。无军官那份先录了两遍、逐 tick 比对相同，所以上面的差异是军官造成的，不是管线的。

## 一条修正够得着哪些单位

每一行都带着 build 存的 `mech_type`，以及——在 build 解析出来的情况下——与之配套的单位
清单：

| `mech_type` | 行数 | 是否列出单位 | 读作 |
| ---: | ---: | --- | --- |
| 10 | 61 | 列出 | 就是这些单位 |
| 0 | 10 | 不列 | 所有单位 |
| 11 | 6 | 不列 | 不针对单位：修正落在塔、护盾或地雷上 |
| 1 | 1 | 列出七个空军单位 | 就是这些单位 |
| 4 | 1 | 不列 | 远程单位 |

类型 10 是常见情形，不需要解读：改进型铁锤列着铁锤，修正的就是铁锤。类型 0 不带清单、
够得着一切，先进进攻战术的 `+0.3` 伤害就是这一类——那正是一方可以持有两份的军官，
`docs/spec/document/layout.md` 把 `officers` 定成多重集就是为了它。类型 11 的行修正的是
`tower_life_rate`、`energy_shield_rate`、`land_mine_rate` 或 `extra_life`，没有一个是单位
的数值。

类型 4 只有一行，先进瞄准系统，射程 `+10`，不带单位清单。build 的数据里没有说明这个类别
选中什么；军官索引的文案说了——"所有**远程**单位射程 +10"——所以这个类别是从效果文案读出来
的，不是从数据读出来的。至于哪些单位算远程，两边都没说。

## 那四个特别的字段修的是什么

有四个字段修正的不是单位的数值，军官索引的文案说明了每一个是什么：

| 字段 | 修正什么 |
| --- | --- |
| `tower_life_rate` | 能量塔的生命；能量塔过载的 `+1` 就是它的"100%" |
| `energy_shield_rate` | 能量护盾装置的护盾；先进护盾装置的 `+0.4` |
| `land_mine_rate` | 哨戒飞弹装置的伤害；先进飞弹装置的 `+2` |
| `super_deployment_time_rate` | 后方部署的传送时间；快速传送的 `-0.5` |

`exp_rate` 是同类里的第五个，也是唯一一个**根本不是比率**的：它的运行时 getter 返回
`int`，五行取值是 `100` 或 `75`，文案写的是"经验成长率 +100%"，所以那个整数就是百分比。

`extra_life` 存得像个单位数值，其实不是。它唯一那一行是紧急避险，文案描述的是一方的生命
被重置为 1，而不是哪个单位多了命——所以这个字段的名字并不是它做的事。

## 本索引未确立的

- **`*_value` 修正怎么合成**，以及同一个数被两条通道修正时谁先谁后。上面那次捕获定下了
  比率，这两条都没够着。
- **哪些单位算"远程"**，即 `mech_type` 4 选中谁，数据和文案都没有列举。
- **上面那四个字段落地之后做什么**：这里还没有任何机制读塔的生命、地雷、护盾装置或部署
  时钟。
